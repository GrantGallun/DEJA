# SmartReplay needs integration and detection validation

**Build SmartReplay from existing replay foundations; treat automatic cross-game event discovery as the experiment.** If GPL distribution fits the project, start with a GameHQ feasibility fork rather than a new recorder. Otherwise, build a focused native player and recorder using appropriately licensed components and WKI-Clipper’s MIT source as a reference. Manual replay over gameplay already has direct product precedent in AMD ReLive; GameHQ also combines continuous recording with an in-game saved-file viewer. Neither establishes SmartReplay’s desired passive picture-in-picture window, separate focus toggle, or measured responsiveness. Start with normal files and frozen replay snapshots, and defer a mutable shared-memory ring until latency measurements justify it. The opportunity is dependable integration and reduced event-setup effort; the evidence does not establish a new replay invention or reliable automatic understanding of unseen games. ([AMD In-Game Replay](https://www.amd.com/en/resources/support-articles/faqs/DH-023.html), [GameHQ viewer](https://github.com/UnderFusion/GameHQ/blob/f8a8ebc6593bc04bdba6a5d8dfca81cfe9e07637/src/ui/qml/components/OverlayViewer.qml#L152))

## Existing products cover replay while repositories supply foundations

AMD documented a hotkey-triggered short replay displayed over the running game, with configurable position, size, and a 5–30-second duration, introduced with Adrenalin 2019 Edition. That is direct product overlap with manual replay in a small overlay. It does not establish separate interaction control, arbitrary seeking or playback speed, cross-vendor support, or current driver/GPU availability; those were not verified. NVIDIA Instant Replay and Medal offer adjacent capture and review workflows, but the inspected documentation gives AMD the clearest direct overlap. ([AMD support](https://www.amd.com/en/resources/support-articles/faqs/DH-023.html), [NVIDIA App](https://www.nvidia.com/en-ph/geforce/news/nvidia-app-download-and-features/), [Medal recording](https://support.medal.tv/support/solutions/articles/48001157618-how-to-make-clips))

GameHQ’s executed behavior matters more than its comments: `OverlayManager::show()` presents without activation, then makes the window activatable and acquires foreground. Its viewer loads `current.fileUrl` into a full-screen overlay gallery. **It is a focused saved-file viewer, not a passive PiP.** A viewer comment says it never takes focus, contradicting the manager; the executed manager path is the stronger evidence. Its README limits overlay support to borderless games. ([Manager](https://github.com/UnderFusion/GameHQ/blob/f8a8ebc6593bc04bdba6a5d8dfca81cfe9e07637/src/overlay/OverlayManager.cpp#L274), [viewer](https://github.com/UnderFusion/GameHQ/blob/f8a8ebc6593bc04bdba6a5d8dfca81cfe9e07637/src/ui/qml/components/OverlayViewer.qml#L5), [README](https://github.com/UnderFusion/GameHQ/blob/f8a8ebc6593bc04bdba6a5d8dfca81cfe9e07637/README.md#L48))

WKI’s save path materializes retained footage, concatenates it, finalizes the output, and returns a filename. RePlays likewise invokes OBS save and retrieves the resulting path; its React player supplies rate, seek, and volume controls. These are useful implementations, but none proves immediate playback from an active rolling buffer. WKI’s README even warns that long saves can take 20–90 seconds, an unreplicated project claim that reinforces the need to measure. ([WKI save](https://github.com/WKImods/WKI-Clipper/blob/1b6aff3e9700b5868d252a3f1108b39c5ae773d9/WKI_Clipper/Services/ReplayBufferService.cs#L1245), [WKI warning](https://github.com/WKImods/WKI-Clipper/blob/1b6aff3e9700b5868d252a3f1108b39c5ae773d9/README.md#L158), [RePlays save](https://github.com/lulzsun/RePlays/blob/db1abe5682ab37c731b1f2fd18412d40dd4eb2f6/Classes/Recorders/LibObsRecorder.cs#L614), [player](https://github.com/lulzsun/RePlays/blob/db1abe5682ab37c731b1f2fd18412d40dd4eb2f6/ClientApp/src/pages/Player.tsx#L389))

## Choose a fork first and freeze each replay session

**The practical default is a bounded GameHQ feasibility fork if GPL is acceptable.** Preserve capture, segment leases, and export isolation; replace the gallery interaction with a compact replay surface. Split visibility from interaction: one hotkey shows or hides playback while the game retains foreground; another explicitly grants controls and later returns input. `OverlayPresenter.cpp` already separates activation styles from presentation, but mouse click-through needs independent hit-testing policy. Add pause, seek, speed, volume, and clear interaction state. ([Presenter](https://github.com/UnderFusion/GameHQ/blob/f8a8ebc6593bc04bdba6a5d8dfca81cfe9e07637/src/overlay/OverlayPresenter.cpp#L40))

Treat the fork as a reference until it builds and passes capture, focus, and playback tests on the target machine. Keep only the application surface that earns its maintenance cost. The decision gate is concrete: can this base preserve game input while showing replay, continue recording during review, and reach an acceptable first-frame delay? If the surrounding gallery architecture obstructs those goals, retain the lessons and use a smaller component host.

If the application must avoid a GPL fork, use a focused native component approach with WGC capture, suitable encoding/playback libraries, and WKI’s MIT generation guards and save logic. Its `FFmpegService.HasEncoderAsync()` performs an actual test encode, a useful capability-check pattern. Hardware encoding does not establish zero-copy capture or low overhead; both WKI and GameHQ include CPU-copy paths. Choose dependencies and measure before committing to a custom renderer. ([Encoder probe](https://github.com/WKImods/WKI-Clipper/blob/1b6aff3e9700b5868d252a3f1108b39c5ae773d9/WKI_Clipper/Services/FFmpegService.cs#L68), [capture command construction](https://github.com/WKImods/WKI-Clipper/blob/1b6aff3e9700b5868d252a3f1108b39c5ae773d9/WKI_Clipper/Services/FFmpegCommandBuilder.cs#L59), [GameHQ encoder](https://github.com/UnderFusion/GameHQ/blob/f8a8ebc6593bc04bdba6a5d8dfca81cfe9e07637/src/capture/SegmentRecorder.cpp#L290))

Begin with a normal finalized file or immutable snapshot while recording continues independently. OBS’s `obs-ffmpeg-mux.c` retains encoded packets, purges around keyframes, references a snapshot, rebases timestamps, and muxes asynchronously. Adopt that ownership principle: **paused playback must retain its media beyond recorder rotation**. A memory map only stores bytes. mpv custom callbacks expose open/read/seek/size/close; they do not supply a timestamp index, protect overwritten bytes, maintain keyframe boundaries, or define a moving retention floor. Even the stream-callback example wraps an ordinary file. ([OBS implementation](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-ffmpeg/obs-ffmpeg-mux.c), [callback contract](https://github.com/mpv-player/mpv/blob/master/include/mpv/stream_cb.h), [example](https://github.com/mpv-player/mpv-examples/blob/e0d1a84c99e8c469b58fde31a1541401acfb0eb2/libmpv/streamcb/simple-streamcb.c))

This first playback path is a latency experiment, not a permanent abandonment of playback without an export. If finalization dominates delay, expose a pinned, keyframe-aligned snapshot through a stable virtual stream. Define logical offsets, generation identity, cancellation, timestamp continuity, and reader lifetime before sharing storage. Stress random seeks while the writer wraps, blocked reads during shutdown, and either process restarting. A frozen session can avoid a user-visible save operation without immediately requiring a continuously moving DVR timeline. ([Stream lifetime requirements](https://github.com/mpv-player/mpv/blob/master/include/mpv/stream_cb.h))

The proposed mpv/D3D11/DirectComposition path needs a version correction. mpv’s D3D11 **render API** entered master on October 15, 2026, labeled API 2.6/mpv 0.42; the retrieved latest stable release, v0.41, lacks that render backend. Ordinary D3D11 video output is a separate feature. The new API requires application-owned device, texture, synchronization, and presentation; it does not supply DirectComposition integration. Isolate it as a pinned development-build experiment after ordinary playback works. ([Addition](https://github.com/mpv-player/mpv/commit/4255130de410e0cbdab694b951085409d466b704), [new contract](https://github.com/mpv-player/mpv/blob/4255130de410e0cbdab694b951085409d466b704/include/mpv/render_d3d11.h), [v0.41 API](https://github.com/mpv-player/mpv/blob/v0.41.0/include/mpv/render.h))

Target borderless games first. DirectComposition does not guarantee visibility over true exclusive fullscreen. Glint instead injects a DLL and hooks `Present`; its sample integration tests do not establish anti-cheat approval or universal compatibility. Also prevent replay audio and imagery from entering subsequent recordings, using appropriate capture selection or exclusion. ([Microsoft presentation guidance](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model), [Glint hooks](https://github.com/kewuamigo/glint-overlay/blob/6e990e89836e82d3badf69cacccf39cea3e8c9d7/core/overlay/overlay-core/src/hook/dx/dxgi.rs), [test scope](https://github.com/kewuamigo/glint-overlay/blob/main/docs/TESTING.md), [process audio capture](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/))

## Event discovery should propose detectors that users confirm

The Python spike discovers recurring visual candidates. `discovery.py` combines intensity-histogram prominence, spatial agreement, and recurrence/run constraints; `grouping.py` groups coactivation; `profile.py` exports unlabeled regions and templates. These operations do not assign arbitrary gameplay meaning. Keep them as proposals: show matched and unmatched examples, let users name or reject candidates, and provide a crop-and-example teaching path when discovery fails. One example initializes a detector; corrections must add positives and hard negatives. ([Discovery](C:/Code/HACKTX/smartreplay/discovery.py), [grouping](C:/Code/HACKTX/smartreplay/grouping.py), [profiles](C:/Code/HACKTX/smartreplay/profile.py))

Sightline already demonstrates exemplar scoring, OCR profiles, previews, and cooldowns. Its author calls it discontinued, while GitHub reports it unarchived; no explicit license was found, so neither permissive reuse nor the GitHub archive flag should be inferred. OverTrack’s Apex and Valorant processors demonstrate pixel-to-event extraction with authored regions, templates, icons, and OCR. GameVideoEdit adds useful coarse-to-fine scanning and multi-frame OCR fusion. **Configurable profiles are established; reducing their creation and repair burden is the stronger product opportunity.** ([Sightline source](https://github.com/SessionGoblin/sightline-computer-vision/blob/main/perception_core/image_detection.py), [author status](https://quacksoftware.com/sightline/), [repository metadata](https://api.github.com/repos/SessionGoblin/sightline-computer-vision), [Valorant processor](https://github.com/overtrack-gg/overtrack-cv/blob/bf45a5393fb4b894ff35b4ee197afbb6852b72d8/overtrack_cv/games/valorant/processors/killfeed/killfeed_processor.py), [GameVideoEdit scanner](https://github.com/Friend-Xu/GameVideoEdit/blob/master/app/core/coarse_to_fine.py))

At runtime, verify confirmed regions with cheap template/edge matching or OCR, multi-frame evidence, hysteresis, and rearming after absence or counter change. Store timestamps, confidence, labels, and provenance. Translate “show my last death” into a query over this event index. Use slower vision/language analysis to suggest unfamiliar labels or inspect ambiguous snippets rather than assuming continuous full-frame reasoning is necessary. This architecture separates semantic flexibility from the cost of repeated detection.

## The research risk is adaptation rather than basic replay

Temporal stability for overlay discovery has substantial adjacent prior art. A 2020 gameplay-analysis study blurred moving scenery through frame averaging and used supervised HUD classifiers. A 2021 TV-logo paper combined unsupervised localization, automatically collected positive/negative examples, and per-stream detector training. Persistent logos differ from intermittent gameplay banners, but automatic discovery followed by detector creation is already an established research direction. The exact SmartReplay combination was not identified in the bounded review; **its novelty is unproven**, and no exhaustive or patentability conclusion follows. ([Gameplay study](https://pmc.ncbi.nlm.nih.gov/articles/PMC7302570/), [2021 logo study](https://www.mdpi.com/2076-3417/11/16/7494))

A 2025 highlights paper fine-tuned X-CLIP on five FPS games; its within-dataset classification results do not establish unseen-game adaptation. Generic X-CLIP source offers video/text similarity machinery, not verified gameplay event weights. SmartReplay’s research risk remains reliable intermittent-event discovery, semantic assignment, and recovery after UI changes. Translucency, animation, rare events, changing names, and static scenery challenge the prototype’s assumptions. ([Highlights paper](https://arxiv.org/html/2505.07721v1), [X-CLIP implementation](https://github.com/microsoft/VideoX/blob/master/X-CLIP/models/xclip.py))

Benchmark real positive and negative clips across held-out sessions and games before claiming automatic adaptability. Compare fixed-region OCR/templates, user-taught crops, simple temporal variance, and the full discovery method; ablate histogram prominence, recurrence, spatial consensus, and grouping. Measure event precision/recall, false saves per hour, duplicates, misses, discovery time, and user corrections across resolution and HUD changes. Repair the audit’s negative-control scorer, cache identity, and reference-label errors before trusting aggregate scores. Synthetic positives plus a Doom negative do not establish real cross-game detection. ([Audit findings](C:/Code/HACKTX/audit/findings.json))

Freeze thresholds before evaluation and label visible event intervals as well as explicit no-event footage. Separate locating a useful UI region from identifying the event and from choosing a useful replay interval; success in one stage can conceal failure in another. Count unknown and rejected cases, and include menus, loading screens, subtitles, moving HUD, ultrawide layouts, and non-FPS footage. Set the acceptable false-save burden and setup effort before choosing the winning detector. The relevant adaptation result is whether users reach dependable event queries with less teaching than the crop baseline.

## Conclusion

**Stage one:** demonstrate ordinary-file PiP with separate visibility and focus controls over real borderless games; record foreground transitions, hotkey-to-first-frame, seek delay, and game frametimes. **Stage two:** connect continuous recording to frozen snapshots, test pause beyond retention and concurrent saves, and measure recorder-only, visible, paused, and hidden overhead. Advance to custom streams or the new D3D11 composition backend only when these measurements identify a bottleneck.

**Stage three:** ship a teachable event index and evaluate discovery against that baseline on held-out games. Keep discovery optional unless it reduces corrections or improves recall at an acceptable false-save rate. Expand compatibility only after testing actual presentation modes, GPUs, HDR, input restoration, capture recursion, and relevant anti-cheat titles. This sequence delivers useful replay independently while making the uncertain adaptation claim measurable.
