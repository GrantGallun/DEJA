# Capture, player, and overlay components: source inspection

## What components are reusable, and what do their implementations actually prove?

### Takeaway
The individual building blocks are real. The strongest reuse is mature libmpv playback, OBS's encoded-packet retention/snapshot pattern, and GameHQ's explicit activation policy. Glint solves a different problem through injection, and its existence does not establish safe universal game compatibility. This research inspected source and documentation only; no downloaded code was executed and no runtime performance was measured.

### Cited Findings
- All four named repositories exist and were publicly accessible: [Glint](https://github.com/kewuamigo/glint-overlay), [GameHQ](https://github.com/UnderFusion/GameHQ), [mpv](https://github.com/mpv-player/mpv), [mpv-examples](https://github.com/mpv-player/mpv-examples). Inspected snapshots: Glint tree `6e990e89836e82d3badf69cacccf39cea3e8c9d7`, GameHQ `f8a8ebc6593bc04bdba6a5d8dfca81cfe9e07637`, examples `e0d1a84c99e8c469b58fde31a1541401acfb0eb2`. [Glint tree](https://api.github.com/repos/kewuamigo/glint-overlay/git/trees/main?recursive=1), [GameHQ tree](https://api.github.com/repos/UnderFusion/GameHQ/git/trees/main?recursive=1), [examples tree](https://api.github.com/repos/mpv-player/mpv-examples/git/trees/master?recursive=1).
- **Glint is an injected overlay.** `core/inject/injector/src/inject.rs::inject_overlay_cef_pipe` calls `inject_overlay_module(pid, ...)`, then creates a CEF IPC address. The file describes its DLL load path using `NtOpenProcess`, `RtlCreateUserThread`, and `LoadLibraryW`. [Source](https://github.com/kewuamigo/glint-overlay/blob/6e990e89836e82d3badf69cacccf39cea3e8c9d7/core/inject/injector/src/inject.rs).
- Its actual rendering integration is not merely a transparent desktop window. `core/overlay/overlay-core/src/hook/dx/dxgi.rs::wrap_swapchain` detours `Present`, `Present1`, `ResizeBuffers`, and other methods. `hooked_present` calls `draw_overlay` before the original Present, dispatching D3D10/11/12 rendering based on device queries. It skips overlay drawing for `DXGI_PRESENT_TEST`. [Source](https://github.com/kewuamigo/glint-overlay/blob/6e990e89836e82d3badf69cacccf39cea3e8c9d7/core/overlay/overlay-core/src/hook/dx/dxgi.rs).
- Glint's documented production design is Electron launcher outside the game, injected overlay DLL, separate CEF UI helper, shared textures, and named-pipe IPC. Its mode model is Hidden / HudPinned / Interactive, which is a useful product-state reference but not a recorder implementation. [Architecture](https://github.com/kewuamigo/glint-overlay/blob/6e990e89836e82d3badf69cacccf39cea3e8c9d7/docs/ARCHITECTURE.md).
- Glint is MIT licensed. It has only five visible public commits, initially published August 7, 2026, with latest commit September 21; release API lists v1.0.0 on September 21 and v0.1.0 on August 7. Latest commit count therefore understates imported internal history but is limited evidence of public maintenance. [README/license](https://github.com/kewuamigo/glint-overlay/blob/main/README.md), [commit history](https://api.github.com/repos/kewuamigo/glint-overlay/commits?per_page=5), [releases](https://api.github.com/repos/kewuamigo/glint-overlay/releases?per_page=3).
- Its integration-test documentation describes injection into a D3D11 SpinningCube sample, IPC/resize/aliveness/metrics checks, gated behind `GLINT_INTEGRATION=1`. That is much narrower evidence than successful operation across popular anti-cheat games. [Testing documentation](https://github.com/kewuamigo/glint-overlay/blob/main/docs/TESTING.md).
- **GameHQ supplies an unusually close focus-policy reference.** In `src/overlay/OverlayPresenter.cpp`, `ensureActivationStyle` applies `WS_EX_NOACTIVATE` while passive; `present` rechecks styles after Qt operations and calls `SetWindowPos(HWND_TOPMOST, ... SWP_NOACTIVATE)`. `makeActivatable` clears the no-activate style separately from foreground acquisition. The code explicitly anticipates native-window recreation resetting styles. [Source](https://github.com/UnderFusion/GameHQ/blob/f8a8ebc6593bc04bdba6a5d8dfca81cfe9e07637/src/overlay/OverlayPresenter.cpp).
- GameHQ's published description identifies C++20/Qt6, WGC, Media Foundation and WASAPI, replay-to-MP4 capture, and no game-process injection. Its core license is GPL-3.0; separately packaged Playnite integration/protocol is MIT. These are project claims, not our measured results. Its root page shows 480 commits and a beta download; another researcher covers recording/player internals. [README](https://github.com/UnderFusion/GameHQ/blob/main/README.md), [repository](https://github.com/UnderFusion/GameHQ).
- **mpv-examples is scaffolding, not rolling replay prior art.** `libmpv/streamcb/simple-streamcb.c` wraps a normal file using `fread`, `fseek`, `fstat`, and `fclose`, then registers `myprotocol` with `mpv_stream_cb_add_ro`. Its seek code itself says it is not 64-bit safe. [Source](https://github.com/mpv-player/mpv-examples/blob/e0d1a84c99e8c469b58fde31a1541401acfb0eb2/libmpv/streamcb/simple-streamcb.c).
- The SDL example demonstrates render-update notification, async player commands, a caller-owned OpenGL context, explicit `mpv_render_context_render`, and caller presentation. It warns against synchronous core calls with advanced render control. The examples' Copyright allows liberal license selection and even consideration as public domain. [SDL source](https://github.com/mpv-player/mpv-examples/blob/master/libmpv/sdl/main.c), [example license](https://github.com/mpv-player/mpv-examples/blob/master/libmpv/Copyright).
- mpv as a whole defaults to GPLv2+, with an LGPLv2.1+ configuration when GPL-only files are excluded; its Copyright explicitly warns that linked libraries, including FFmpeg configuration, can change the resulting binary's license. Do not infer the library binary's license solely from permissive API header licenses. [Copyright](https://github.com/mpv-player/mpv/blob/master/Copyright).

### Inferences
- Reuse GameHQ's separation between showing a passive window and explicitly granting interaction for F8/F9 semantics; adapt it rather than assuming every Qt/Win32 show call preserves foreground. No-activate is also distinct from mouse click-through, which needs its own implementation and tests. Basis: [OverlayPresenter](https://github.com/UnderFusion/GameHQ/blob/main/src/overlay/OverlayPresenter.cpp).
- Glint is a possible optional injected backend research reference, not the lowest-risk baseline for a game-agnostic recorder. Its public source proves hook mechanics, not anti-cheat approval or ban safety. Basis: [injector](https://github.com/kewuamigo/glint-overlay/blob/main/core/inject/injector/src/inject.rs), [test scope](https://github.com/kewuamigo/glint-overlay/blob/main/docs/TESTING.md).

### Gaps
- No runtime build, game compatibility matrix, anti-cheat approval, input latency, startup latency, or overhead benchmark was established here. None of these repositories should be described as measured proof of SmartReplay's complete target behavior.

## Does the proposed libmpv + DirectComposition + rolling MPEG-TS architecture work as stated?

### Takeaway
It is a plausible engineering proposal with substantial unimplemented contracts. A material time-sensitive correction: mpv **now has a D3D11 render API on master**, added October 15, 2026, but the latest published release retrieved was v0.41.0 from December 21, 2025. Treat direct D3D11 rendering as a pinned development-build experiment, not an established feature of an arbitrary shipped libmpv DLL.

### Cited Findings
- Commit `4255130de410e0cbdab694b951085409d466b704` adds the D3D11 backend. Commit API records committer date October 15, 2026 (author date April 17); API changelog labels it mpv 0.42.0 / client API 2.6. The latest-release endpoint returns v0.41.0 published December 21, 2025. [Exact commit/diff](https://github.com/mpv-player/mpv/commit/4255130de410e0cbdab694b951085409d466b704), [commit metadata](https://api.github.com/repos/mpv-player/mpv/commits?path=include/mpv/render_d3d11.h&per_page=3), [latest release](https://api.github.com/repos/mpv-player/mpv/releases/latest).
- Release v0.41.0's `include/mpv/render.h` lists OpenGL and software render backends, with `wid` as another window-embedding option. It warns about render-thread/core deadlocks; software rendering performs scaling/conversion/OSD on the CPU and is characterized as slow. Current master additionally lists D3D11. This distinction is **render API**, not a claim that the ordinary mpv executable lacked D3D11 video output. [v0.41 header](https://github.com/mpv-player/mpv/blob/v0.41.0/include/mpv/render.h), [master header](https://github.com/mpv-player/mpv/blob/master/include/mpv/render.h).
- New `render_d3d11.h` requires an application-supplied `ID3D11Device`; each render targets an application-owned texture on that same device. Texture requirements include render-target bind, default usage, and no multisampling/array/mipmaps; sRGB formats are unsupported. The host owns presentation. mpv does not restore immediate-context state; other threads cannot use it concurrently. Different-device texture use needs host synchronization. `d3d11va` can decode on the supplied device, but single-threaded devices restrict this to copy-back modes. [Exact-version header](https://github.com/mpv-player/mpv/blob/4255130de410e0cbdab694b951085409d466b704/include/mpv/render_d3d11.h).
- Actual backend code exists: `video/out/d3d11/libmpv_d3d11.c::init` creates the D3D11 rendering abstraction, `wrap_fbo` wraps the supplied texture and checks render-target support, and `done_frame` flushes and releases the wrapper. This is real source, not just declarations; it still supplies no DComp swapchain or UI composition integration. [Source](https://github.com/mpv-player/mpv/blob/4255130de410e0cbdab694b951085409d466b704/video/out/d3d11/libmpv_d3d11.c).
- `IDXGIFactory2::CreateSwapChainForComposition` creates a swapchain usable in a DirectComposition visual tree; it requires flip-sequential and stretch scaling. `SetFullscreenState`, `ResizeTarget`, and several window-oriented operations are not valid for this composition swapchain. [Microsoft API](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgifactory2-createswapchainforcomposition).
- WebView2's composition controller supports visual hosting, including a root visual target and explicit mouse/pointer input delivery. The regular controller handles sizing, visibility, and focus. This validates a potential composition host mechanism, not automatic input routing, libmpv interop, or low overhead. [Microsoft reference](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2compositioncontroller?view=webview2-1.0.3537.50).
- `include/mpv/stream_cb.h` documents custom **byte** open/read/seek/size/close callbacks. Empty reads mean final EOF; a reader with no available data must block until data exists. mpv probes seekability by seeking to byte zero at open. Streams remain valid until mpv closes them; the caller cannot directly close them through this API. A cancel callback interrupts reads/seeks from another thread and must not block. Callbacks cannot call the same libmpv instance because of deadlock. The header still labels the API unstable. [Header](https://github.com/mpv-player/mpv/blob/master/include/mpv/stream_cb.h).
- Actual `stream/stream_cb.c` delegates `fill_buffer`, `seek`, and `get_size` to those callbacks; successful seek-to-zero turns on `stream->seekable`. It does not implement a moving retention floor, time index, overwrite protocol, buffer pinning, or MPEG-TS repair. [Source](https://github.com/mpv-player/mpv/blob/master/stream/stream_cb.c).
- OBS's actual replay buffer is in `plugins/obs-ffmpeg/obs-ffmpeg-mux.c`, not a standalone replay-buffer file. `replay_buffer_data` retains encoded packets; purge logic discards GOP-aligned data using keyframes; `replay_buffer_save` builds a referenced packet snapshot, rebases timestamps and launches a mux thread. Registered procedures are `save()` and `get_last_replay(out string path)`, with `saving`/`saved` signals. This is a saved-file output contract, not an API returning an already seekable live ring to a player. Source is GPLv2+. [Source](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-ffmpeg/obs-ffmpeg-mux.c).

### Inferences
- D3D11 render-to-composition-swapchain-backbuffer is now technically plausible without an OpenGL-to-D3D bridge, but needs a build including the new backend and compatible dependencies, device/texture/thread ownership, alpha/color-space checks, resize/device-loss handling, and verified presentation. Basis: [new backend](https://github.com/mpv-player/mpv/blob/4255130de410e0cbdab694b951085409d466b704/video/out/d3d11/libmpv_d3d11.c), [DComp API](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgifactory2-createswapchainforcomposition).
- A memory map is transport/storage, not a solution to seeking. Reusing byte offsets after ring wrap can make a player's cached positions point at different media. Growing size and an advancing oldest-byte boundary require a defined logical offset space and retention contract. TS packet alignment is insufficient without keyframes, headers, timestamp continuity and lifetime handling. These are design deductions from the byte callback and packet snapshot contracts, not an observed libmpv failure. [Callback contract](https://github.com/mpv-player/mpv/blob/master/include/mpv/stream_cb.h), [OBS snapshot pattern](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-ffmpeg/obs-ffmpeg-mux.c).
- Lowest-risk model is a frozen replay session: pin/refcount a keyframe-aligned range when F8 opens, expose an immutable virtual stream or normal finalized file, let recording retain new data independently, release the session after close. A paused replay must not allow recorder pruning to overwrite bytes still referenced by the player. Follow the snapshot pattern before attempting a continuously moving DVR timeline. [OBS snapshot source](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-ffmpeg/obs-ffmpeg-mux.c), [stream lifetime contract](https://github.com/mpv-player/mpv/blob/master/include/mpv/stream_cb.h).

### Gaps
- No repository inspected implements the precise WGC → encoder → mutable memory-mapped TS ring → libmpv callback → DComp/WebView2 pipeline end-to-end.
- No proof here that libmpv demuxer indexing tolerates a shrinking/moving virtual file or updates its time range correctly after wrap. No direct confirmed master D3D11 example was present in mpv-examples' retrieved tree. WebView2 is optional UI complexity, not a proven performance requirement.

## What constraints and experiments should determine the staged implementation?

### Takeaway
Build a small passive topmost player over borderless games first, use frozen snapshots and existing capture/replay infrastructure, then optimize storage only after measured bottlenecks. Universal true-exclusive-fullscreen visibility and anti-cheat approval remain separate product risks, not problems automatically solved by DirectComposition or API selection.

### Cited Findings
- Microsoft's flip-model guidance distinguishes classic exclusive fullscreen from windowed DirectFlip/Independent Flip. When desktop content appears above a flip-model application, DWM can resume composition, reverse-compose, or use MPO. It recommends PresentMon to inspect what actually happens. These statements support borderless/flip-model overlay feasibility; they do **not** promise ordinary windows appear over every true exclusive-fullscreen game. [Microsoft guidance](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model).
- WGC provides application-window/display capture, a D3D11 frame pool, `FrameArrived` notifications and `TryGetNextFrame`. Microsoft recommends avoiding heavy UI-thread work on frame arrival. HDR capture may require float16 throughout and tone mapping. This validates frame acquisition, not zero-copy encoding, recorder overhead or universal content availability. [Screen capture documentation](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture).
- Microsoft's process-loopback sample supports including a target PID and children or excluding that tree from system audio. It is independent of a particular endpoint and requires Windows build 20348 or later; processes without render streams produce silence. This minimum differs from baseline WGC support and must be checked separately. [Microsoft sample documentation](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/).
- The implementation is concrete: `CLoopbackCapture::ActivateAudioInterface` fills `AUDIOCLIENT_ACTIVATION_PARAMS`, selects `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` or EXCLUDE, sets the target PID, and calls `ActivateAudioInterfaceAsync(VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK, ...)`. `ActivateCompleted` initializes a shared-mode loopback event-driven audio client and gets `IAudioCaptureClient`. [Source](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/ApplicationLoopback/cpp/LoopbackCapture.cpp).
- `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` supports excluding the app's own top-level recording-control window beginning Windows 10 version 2004, and requires DWM composition. Earlier versions treat it as WDA_MONITOR. It is a public capture-exclusion mechanism, not a security guarantee. [Microsoft API](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity).

### Inferences
- **Stage 1: validate the product contract with ordinary files.** F8 shows/hides a small `WS_EX_NOACTIVATE` topmost window and never changes `GetForegroundWindow`; F9 explicitly enters interaction. Implement mouse hit-testing/click-through independently. Use libmpv normal file playback for ±5 seconds, pause, 0.25–2× speed, volume and mute. Log foreground before/after every transition. Reuse the precise GameHQ presentation model. [Reference](https://github.com/UnderFusion/GameHQ/blob/main/src/overlay/OverlayPresenter.cpp).
- **Stage 2: retain recording while replaying a frozen capture.** Use an existing recorder/OBS save-first proof; measure trigger-to-play delay. If that meets the UX, stop adding storage complexity. For a custom recorder, use keyframe-aligned immutable segments/packet snapshots and reader leases. Separate recorder/player processes are reasonable fault isolation, but not inherently necessary for speed. [OBS retention/snapshot reference](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-ffmpeg/obs-ffmpeg-mux.c).
- **Stage 3: isolate the new D3D11 composition spike.** Pin mpv after the exact new commit; decode and render one normal file into a composition swapchain before adding WebView2 or a ring. Verify device sharing, transparency, HDR/SDR colors, resize and device loss, idle/hidden render cost. An older stable `wid` or OpenGL path remains a separate comparison experiment. [New API](https://github.com/mpv-player/mpv/blob/4255130de410e0cbdab694b951085409d466b704/include/mpv/render_d3d11.h), [stable API](https://github.com/mpv-player/mpv/blob/v0.41.0/include/mpv/render.h).
- **Stage 4: only if latency measurements require it, implement custom-stream snapshots.** Stress hundreds of random seeks; pause longer than retention; open/close repeatedly while the writer wraps; crash/restart either process; test cancellation while blocked at end; verify stale-generation detection and stable logical offsets. Freeze duration for a session before attempting moving-live-range semantics. [Required callback/lifetime contract](https://github.com/mpv-player/mpv/blob/master/include/mpv/stream_cb.h).
- Measure recorder-only, player-visible, player-paused, and hidden modes separately: game frame-time distribution, capture/encode drops, GPU copy/encode/decode usage, CPU, working set, memory/disk bandwidth, trigger-to-first-frame and seek latency. Test windowed/borderless/actual exclusive with PresentMon, DX11/12/Vulkan/OpenGL, HDR, high-refresh/VRR, multi-monitor/hybrid GPU, and elevated games. A small demo passing is not evidence of universal behavior. [Presentation-mode basis](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model).
- Capture game-only audio where supported to prevent replay audio recursively entering future recordings. With whole-system loopback, explicitly solve playback exclusion or accept audio recursion; do not assume a visual no-injection design solves it. Similarly, test whether monitor capture includes the overlay and use window capture or capture exclusion. [Process audio modes](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/), [window exclusion](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity).

### Gaps
- Anti-cheat compatibility needs each relevant vendor/game's supported integration rules and real compatibility tests; this research establishes neither approval nor ban safety for Glint or a custom overlay.
- True exclusive fullscreen may force an explicitly limited compatibility promise, a supported platform overlay integration, or a separate injected backend. No authoritative source inspected establishes a universal non-injected solution.
- The frontier is reliable integration and compatibility under the combined requirements, especially instantaneous replay session retention plus focus/input behavior plus fullscreen/anti-cheat. Capture, hardware encoding, media playback and topmost passive windows are established components; their combination at the desired guarantees is not demonstrated by merely listing APIs.
